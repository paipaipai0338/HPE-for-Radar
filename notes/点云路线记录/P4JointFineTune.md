# P4JointFineTune：保持结构不变的联合微调

这是冻结编码器实验的第二阶段：保留 P4 编码器、逐关节交叉注意力、GRU 与原坐标输出头的结构，从 `experiments/P4JointMemory/20261102_164747/best.pth`（epoch 37）初始化解码器，编码器加载其对应的原 P4 最佳权重。该源模型同帧 MPJPE 为 12.9256 cm，反向 1705 帧。

逻辑批量为16×128，保留完整128帧解码器梯度。编码器按64个窗口分批，并在训练时使用非重入梯度检查点重计算。每个逻辑批次只执行一次参数更新，预计每轮约500次（依轨迹长度和打乱顺序变化）。编码器从原P4最佳权重初始化，解码器从冻结编码器实验第37轮最佳权重初始化。

## 训练方式

- 前 5 轮解冻 P4 Transformer 和位置编码，保持 P4DConv 冻结；从第 6 轮开始共同训练 P4DConv。
- 编码器学习率 `1e-5`，新解码模块 `1e-4`，坐标输出头 `1e-5`。AdamW，最多 20 轮，patience 5；切换至全编码器阶段时重置早停计数。
- 保留原 16 帧输入、acc_frame=3、200 点、原人员/组划分、不中心化与 low 坐标监督。P4 仍读取 high 坐标，输出按标定转换到 low。
- 保持原 MPJPE、近水平样本权重 2、方向损失系数 0.02。沿用解码器的 token 和连续缺测增强；不额外引入原始点云增强来混淆这个实验。
- 每批16条轨迹、每条128帧，整个128帧解码完成后统一反向与更新一次，再截断跨批次梯度；跨批次保留记忆数值。遮挡掩码仍按整段128帧生成。
- `encoder_batch_size: 64` 只限制一次送入P4的窗口数，不切断解码器历史梯度、不触发额外optimizer.step。`checkpoint_encoder: true` 使反向时重新计算编码器激活，以计算时间换显存；无需新增磁盘缓存。
- P4 用 BF16，几何变换与解码器用 FP32；在线构造的输入点坐标为 FP32。

它验证的是编码器与解码器共同适应是否有效，不是全随机初始化实验。它继承了此前训练进度，不能与相同轮数但随机初始化的模型直接比较训练预算。

## 启动

配置：`run/p4_joint_finetune.yaml`，默认 `cuda:1`。

```bash
conda activate pytorch
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 python -m run.train_p4_joint_finetune
```

首次只建立紧凑轨迹索引，再从原 FFTGen 文件在线读取点云，不保存重叠窗口。也可以先仅建立索引：

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 python -m run.train_p4_joint_finetune --prepare-only
```

小规模工程检查：

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 python -m run.train_p4_joint_finetune --smoke
```

`--smoke` 只选训练/验证首组的前 128 个有效窗口，训练 2 轮，第一轮冻结 P4DConv、第二轮解冻，输出目录前缀 `smoke_`。不能用它评价精度。

## 在线输入和评估

默认不生成点云窗口 NPY 文件。`outputs/p4_joint_finetune/index/` 只保存源轨迹行号和数据窗口索引，标注、质量与 P4 对照预测复用已有实验缓存。已为全量数据建立索引：训练 772060 帧、验证 104136 帧，与源实验完全相同；索引文件约 16.3 MiB，连同完整清单约 24 MiB。它仍依赖原 FFTGen 文件和原实验的证据缓存，后者未复制为新的大文件。

DataLoader 使用 4 个持久 worker 在线加载、身份对齐、裁剪和确定性采样。每个 worker 最多复用 256 个原始帧对象，返回副本避免缓存被修改；每次最多合并 `input_batch_size=16` 个窗口进行 CPU 预处理。训练仍逐块异步传入 GPU，不将全部点云存入内存。

读取时核对源时间戳、人体目标与标定；身份歧义、时间间隔异常、标定或目标变化会报错。索引按组原子保存，所有源验证帧必须保持覆盖。磁盘占用降低的代价是每轮需重复在线预处理；多进程预取和有上限的原始帧复用用于减少等待。

初始 epoch 0 在线验证与源模型的全验证集误差必须相差小于 0.5 mm，否则中止。逐轮报告与原流程相同的 all/cold/warm、根误差、相对误差、每组误差与方向错误；最佳按包含冷启动帧的全部 MPJPE 选择。原 P4 基线使用旧实验保存的同帧预测，始终固定。

输出在 `experiments/P4JointFineTune/<时间戳>/`，保存编码器与解码器的联合权重、优化器状态、配置、模型源码、初始化检查点、证据清单、history。源模型和旧实验不修改。

## 查看新权重

```bash
python -m run.analyze_pose_refiner --experiment experiments/P4JointFineTune/<时间戳> --checkpoint best.pth --device cuda:1
```

新模型诊断必须在线运行 P4，所以需要 CUDA 和 pointnet2 扩展。脚本会加载联合训练后的编码器并在线读取原 FFTGen 点云，不会把新解码器误接到旧的冻结 token 缓存。结果仍写入 `diagnosis_best.json`。旧模型继续使用旧缓存诊断。原冻结-token 消融脚本拒绝联合权重，避免产生错误的消融结论。

## 工程验证

在线读取与原预处理输入一致，29项相关测试通过，覆盖：普通计算与梯度检查点的预测/参数梯度等价、完整128帧的末帧损失可回传至首帧、每批仅一次参数更新、多人身份与原有进度显示。

真实FFTGen检查中，BF16编码器与pointnet2原生算子的普通/重计算参数梯度最大差为0；完整16条轨迹×128帧、编码器微批64的前向/反向峰值分配显存约4.51GB，耗时约1.88秒。该计时只覆盖内存中已有点云的模型计算，不代表在线全量训练速度，也不包含其他GPU进程的占用。

两阶段真实冒烟验证每轮只更新1次（各128个有效训练帧），阶段1冻结P4DConv、阶段2其梯度非零；新权重在线诊断通过。全量轨迹索引按seed42模拟为489批/轮，接近原训练约496次/轮。

修正版 `20261103_112734` 已在第10轮早停，最佳第4轮12.8436cm，比初始化12.9255cm改善约0.82mm；第6轮起解冻P4DConv后没有超过此最佳。每轮约488–516次更新，修正后的预算符合预期。完整结果见 `experiments/P4JointFineTune/20261103_112734/training_review.md`。这是小幅收益，距离10cm仍有差距；原GT裁剪和离线身份关联限制仍保留。
